# Supabase 快照读取超时修复与验证

验证日期：2026-10-29。代码基于 `a5aa58b`，Supabase 项目为 `bkfqklqxjcjbcstpyqxo`。

## 问题与修复

数据库日志确认 `tripmate_snapshot()` 曾因 statement timeout 被取消，SQLSTATE 为 `57014`。PR #32 已将普通版本冲突改用 `PT409`，但读取完整快照的成本仍然存在。

本次检查时，快照包含 463 条 records、628 条 traces、147 条 commands，业务版本为 350。三个集合的内容转成文本约 13.32 MiB，不含外层包装。原 SQL 函数在受控执行中产生 1,783 个临时块的读取和写入（每块 8 KiB），而直接执行函数体查询没有该临时读写。这支持函数返回大结果时的物化开销是本次可消除的一项成本；不代表历史超时只有这一种原因。

迁移将函数改为 PL/pgSQL 标量返回，在一个 SQL 语句内构造相同的 JSON。函数标记为 STABLE，保持只读语义及统一的语句快照。没有删除业务记录、审计历史或去重记录，没有改动版本冲突逻辑，也没有提高数据库全局内存或超时时间。

保留现有 SECURITY DEFINER、空 search_path 和仅供后端使用的访问权限。匿名用户及普通登录用户仍不能执行该函数。

## 验证结果

- 原函数体与新函数在同一个 SQL 语句内比较：JSON 完全一致；版本及三个集合数量均保持不变。
- `SELECT public.tripmate_snapshot()`：修复前约 1,812.802 ms，修复后约 904.370 ms；临时块读写从各 1,783 降为 0。
- 按实际 PostgREST 返回包装执行数据库查询：约 981.566 ms，临时块读写为 0。
- 切换为 service_role 后可以调用，返回 JSON object；anon 与 authenticated 的 EXECUTE 权限检查均为 false。
- 检查函数所有者、STABLE、SECURITY DEFINER 和 search_path：符合预期。
- 最新 main 基础上的 Python 回归：292 tests，150.198 秒，全部通过。
- 修复后安全及性能建议中没有新增条目；既有建议未在本次修改中扩大处理范围。

上述耗时是当前数据量下的单次受控测量，不能作为响应时间承诺。API 包装测试在数据库内执行，未包含 HTTP 网络、后端及浏览器总耗时。Python 回归也不能替代真实账户的页面验收。
